# Unity 战斗系统 Architecture V2.0

**Combat System Architecture · Technical Design Baseline · V2.0**

- 项目：基于现有 Unity 工程的《明日方舟：终末地》风格战斗 DEMO
- 文档类型：总体架构规范（Architecture Specification）
- 用途：作为用户与 Codex 交互、模块设计评审和逐模块实施的共同基线
- 当前阶段：重新设计与实现；此前战斗系统代码实现已回撤
- 本文范围：总体模块地图、职责边界、依赖关系、目录结构、实施顺序、验收规范
- 本文不包含：业务代码实现、场景修改、Prefab 修改、资源迁移

## 0. 项目基线与设计约束

### 0.1 项目现状

本项目以用户现有 Unity 工程为基础重新设计战斗系统。此前战斗系统代码实现已经回撤，因此不得假设历史战斗类、接口或目录仍然存在

需要保留并复用的现有内容：

- 两个已有角色：大剑角色、双手剑角色
- 对应角色模型、材质、贴图和动画资源
- 现有武器资源
- 现有环境与 CombatDemo 场景
- 现有输入配置，以及可复用的相机和 UI 资源

此前检查得到的工程配置如下，正式执行 M0 时必须重新核对实际工程：

| 项目 | 此前检查到的配置 |
| --- | --- |
| Unity | 6000.3.28f1 |
| Render Pipeline | URP 17.3.0 |
| Cinemachine | 3.1.7 |
| Input System | 1.20.1 |
| AI Navigation | 2.0.16 |
| Timeline | 1.8.13 |
| UGUI | 2.0.0 |

项目参考仓库：<https://github.com/emt11/Arknights-Endfield-Demo>

明确限制：不阅读仓库中的 `Docs/` 和 `Assets/Scripts/` 旧实现，不将其作为新架构依赖

### 0.2 核心技术约束

| 领域 | 架构要求 |
| --- | --- |
| 战斗动画 | 使用 Unity Playables API 驱动 |
| 基础移动动画 | 可以使用 Animator Controller / AnimatorControllerPlayable |
| 攻击动画 | 使用 AnimationClipPlayable |
| 动画混合 | 使用 AnimationMixerPlayable、AnimationLayerMixerPlayable 等适合的 Playable |
| Root Motion | 统一提取、修正和消费 |
| Motion Warping | 自定义运动扭曲系统 |
| 角色移动 | 统一通过 CharacterMotor 应用最终位移 |
| 命中检测 | 武器轨迹连续扫掠 + Physics Query |
| 对象池 | Effect、Audio、Projectile、临时 UI 等复用对象统一池化 |
| 属性 | 独立 StatSystem |
| 角色成长 | 独立 CharacterBuild |
| 伤害 | 独立 DamageSystem |
| 配置 | 静态配置优先使用 ScriptableObject |
| 测试 | 使用 Unity Test Framework，按模块验收 |

### 0.3 全局架构原则

1. 一次只设计或实现一个模块
2. 模块必须先完成设计评审，再开始编码
3. 不允许 Codex 未经批准顺手实现其他模块
4. 不允许未经批准修改已验收模块
5. 不允许为了当前模块方便而破坏其他模块的职责边界
6. 所有跨模块协作通过公开接口或明确的事件契约完成
7. 不允许多个模块同时拥有同一份可变运行时数据
8. 未实际执行的编译、测试和运行验证必须标记为未验证
9. 不创建大量无实际用途的空目录、空类或占位实现
10. 架构图中的模块数量不代表必须创建同等数量的 Unity Package 或 Assembly Definition

## 一、总体架构与领域分层

整个战斗系统划分为六个领域层。它们是逻辑职责分组，不是强制的程序集分组

### 1.1 Gameplay Orchestration：游戏流程层

包含：

- CombatSession
- Actors
- Party
- Input
- AI
- Encounter

负责战斗会话、角色组织、玩家输入、队伍管理、AI 决策和战斗流程

### 1.2 Character Foundation：角色基础层

包含：

- CharacterBuild
- Stats
- Resources
- Effects
- Status

负责角色构建、属性、动态资源、持续效果和战斗状态

### 1.3 Combat Execution：战斗执行层

战斗执行代码统一归入 `Assets/Scripts/Runtime/Combat/`，六个子模块各自维护公开接口和命名空间

| 子模块 | 核心职责 | 命名空间 |
| --- | --- | --- |
| Actions | 处理动作请求、执行、取消与时间轴窗口 | `Endfield.Combat.Actions` |
| Weapons | 管理武器定义、实例、骨骼挂载和轨迹采样点 | `Endfield.Combat.Weapons` |
| HitDetection | 在命中窗口内执行扫掠查询、筛选目标并生成命中上下文 | `Endfield.Combat.HitDetection` |
| Damage | 根据快照计算伤害，通过资源接口应用结果并发布结算事件 | `Endfield.Combat.Damage` |
| Combos | 管理普攻连招树、输入缓存、分支和连招游标 | `Endfield.Combat.Combos` |
| Skills | 管理战技与终结技的请求、消耗和冷却，通过 Actions 提交动作 | `Endfield.Combat.Skills` |

### 1.4 Animation & Motion：动画与运动层

包含：

- Animation
- CharacterMotion
- MotionWarping

负责 PlayableGraph、动画混合、角色移动、Root Motion 和 Motion Warping

### 1.5 Infrastructure：基础设施层

包含：

- CombatContracts
- Timing
- Pooling
- Diagnostics

负责跨模块数据契约、时间管理、对象池和调试诊断

### 1.6 Presentation：表现层

包含：

- Presentation
- UI

负责特效、音效、镜头反馈、伤害数字、战斗 HUD 和状态显示

## 二、完整模块地图与职责边界

### 2.1 Gameplay Orchestration

#### 01. CombatSession

**职责**

- 创建和销毁一次战斗会话
- 管理战斗生命周期
- 组织模块初始化和清理
- 绑定现有场景中的战斗引用
- 管理战斗重试和重置

**不负责**

- 逐帧执行攻击逻辑
- 伤害公式
- 敌人 AI 决策

#### 02. Actors

**职责**

- 定义战斗单位身份
- 管理阵营和阵营关系
- 组合角色运行时模块
- 提供统一 Combatant 能力
- 管理单位存活状态和生命周期

**不负责**

- 装备成长计算
- 伤害公式
- 动画图内部播放逻辑

#### 03. Party

**职责**

- 管理队伍成员和槽位
- 管理当前操控角色
- 角色切换
- 队伍共享资源
- 队友与队伍协同规则

首版只要求两个有效角色，数据结构支持四个槽位。四槽位架构不等于首版必须制作四个完整角色

#### 04. Input

**职责**

- 接收 Unity Input System 输入
- 生成输入命令
- 管理输入缓存
- 处理输入优先级和过期

**不负责**

- 直接播放动画
- 直接扣除敌人生命值
- 绕过 ActionSystem 执行动作

#### 05. AI

**职责**

- 敌人决策
- 队友辅助决策
- 目标选择
- 攻击策略
- 移动与战斗站位决策

玩家输入和 AI 决策最终通过统一的动作请求接口执行。首版优先使用有限状态机与简单选择器，不预先开发通用行为树编辑器

#### 06. Encounter

**职责**

- 敌人生成
- 波次管理
- Boss 阶段
- 战斗胜负条件
- 战斗流程编排

**不负责**

- 敌人每一帧的攻击行为
- 伤害计算
- 角色动画播放

### 2.2 Character Foundation

#### 07. CharacterBuild

**职责**

- 角色基础属性来源
- 等级成长
- 主属性、副属性
- 武器属性聚合
- 装备和天赋属性聚合
- 生成角色初始 StatSet

**不负责**

- 属性修改器底层计算
- 伤害公式
- Buff 生命周期

#### 08. Stats

**职责**

- 属性定义
- 运行时属性实例
- 属性修改器
- 派生属性
- 属性依赖关系
- 缓存与 Dirty 传播
- 属性来源追踪
- 属性变化事件

建议支持的属性分类：

- Primary Attributes：STR、AGI、INT、WIL
- Base Combat Stats：BaseATK、BaseDEF、BaseHP、FixedATK 等
- Derived Stats：ATK、DEF、MaxHP、CritRate、CritDamage、伤害加成、抗性和治疗属性
- Special Stats：AttackSpeed、MoveSpeed、StaggerDamageBonus、UltimateGain 等

**边界规则**

- MaxHP 是 Stat
- CurrentHP 是 Resource
- PhysicalResistance 是 Stat
- Vulnerability 层数是 Status
- StatSystem 不依赖 Damage、UI 或 Animation

属性系统参考用户此前提供的《设计属性系统.txt》，包括 StatDefinition、StatInstance、StatSet、StatModifier、StatDependencyGraph、SourceID 和缓存机制。具体游戏数值及公式必须标记为待验证或 Demo 自定义规则，不能把参考资料中的数值直接当成原作内部实现

#### 09. Resources

**职责**

- HP 当前值
- SP
- 终结技能量
- 护盾
- 失衡槽等动态资源

边界规则：

- MaxHP 属于 Stats
- CurrentHP 属于 Resources
- MaxSP 属于 Stats 或相应上限配置
- CurrentSP 属于 Resources
- 护盾实例由 Resources 管理
- 失衡状态转换由 Status 管理，失衡数值槽可由 Resources 或 Status 内部专用数据管理，但必须确定唯一所有者

#### 10. Effects

**职责**

- Buff、Debuff 生命周期
- 持续时间
- 周期性效果
- 叠加策略
- 来源追踪
- 添加和移除 StatModifier
- 添加和移除 DamageModifier

**不负责**

- 元素附着规则
- 伤害命中判定
- 直接控制动画

#### 11. Status

**职责**

- 元素附着
- 脆弱
- 控制状态
- 失衡状态转换
- 元素反应
- 状态层数和消费规则

Status 表达战斗状态；Effect 表达持续效果实例。两者必须分离

### 2.3 Combat Execution

#### 12. Actions

**职责**

- 动作请求和提交
- ActionInstance 生命周期
- 动作取消
- 动作优先级
- 动作时间轴
- 动作窗口管理

ActionSystem 是动作执行协调者，不是动画播放器

#### 13. Weapons

**职责**

- 武器定义
- 武器 Prefab 实例
- 武器骨骼挂载
- 武器局部偏移
- 武器轨迹采样点

**不负责**

- 攻击伤害结算
- 目标 HP 修改

#### 14. HitDetection

**职责**

- Blade Sweep
- SphereCast / CapsuleCast
- 范围命中查询
- Hit Window 管理
- 命中目标筛选
- AttackID / HitWindowID 去重
- HitContext 生成

**不负责**

- 最终伤害公式
- Buff 生命周期
- UI 反馈

#### 15. Damage

**职责**

- 攻击属性快照
- DamageContext
- DamageModifier
- 暴击计算
- 防御和抗性
- 伤害乘区
- DamageBreakdown
- DamageResult
- 伤害应用和结算事件

DamageSystem 不负责判断攻击是否命中，也不直接修改角色基础属性

#### 16. Combos

**职责**

- 普攻连招树
- 连招输入窗口
- 连招输入缓存
- 分支条件
- 连招循环
- 连招游标管理

普攻连招和队伍连携是不同机制。队伍连携归 Party 或 Party 内的 TeamCombo 子模块

#### 17. Skills

**职责**

- 战技请求
- 终结技请求
- 技能冷却
- 技能资源消耗
- 目标要求
- 技能动作配置
- 技能效果触发

技能通过 Actions 执行动作，不直接实现另一套动画播放系统

### 2.4 Animation & Motion

#### 18. Animation

**职责**

- PlayableGraph 生命周期
- AnimatorControllerPlayable 基础动画输入
- AnimationClipPlayable 战斗动画
- AnimationMixerPlayable 动作混合
- AnimationLayerMixerPlayable 动画层
- 动画速度与时间控制
- 动画混合与退出

**不负责**

- 角色最终位移
- 攻击命中
- 伤害结算

#### 19. CharacterMotion

**职责**

- CharacterMotor
- 地面检测
- 重力
- 移动和转向
- Root Motion 消费
- 外部冲量
- 碰撞约束
- 最终 Transform 运动应用

所有角色位移必须通过 CharacterMotor

#### 20. MotionWarping

**职责**

- Root Motion 轨迹采样数据
- MotionProfile
- Warp Target
- Warp Window
- 位移补偿
- 旋转修正
- 碰撞反馈
- 目标丢失处理

MotionWarping 提供受约束的运动修正，不直接修改 Transform.position

### 2.5 Infrastructure

#### CombatContracts

只放跨模块共享的稳定数据契约、标识、接口和上下文。不得成为无边界的 Common 或 Utils 收纳目录

#### Timing

负责战斗时间、动作时间、暂停、慢速和局部 Hit Stop 的时间规则。PlayableGraph 的更新模式必须在技术验证阶段确定

#### Pooling

负责对象租用、归还、重置、预热、容量管理和会话清理。Effect、Audio、Projectile、临时 UI 等按生命周期纳入对象池

#### Diagnostics

负责战斗事件追踪、属性调试、动作调试、运动轨迹诊断和必要的性能诊断

### 2.6 Presentation

#### Presentation

负责特效、音效、镜头震动、Hit Flash、Hit Stop 表现请求、伤害数字等视觉与听觉反馈。临时对象通过 Pooling 获取和归还

#### UI

负责 HUD、角色面板、技能状态、敌人血条、状态图标和调试展示。UI 只读取数据和订阅事件，不拥有战斗业务数据

## 三、模块依赖关系

### 3.1 总体依赖原则

建议采用以下依赖层次：

1. Foundation / Contracts 提供稳定基础类型
2. Stats、Resources 提供独立数据能力
3. CharacterBuild、Effects、Status 通过公开接口使用基础数据能力
4. Actors 组合角色运行时模块
5. Animation、CharacterMotion、MotionWarping 提供动画与运动能力
6. Actions、Weapons、HitDetection、Damage、Combos、Skills 组织战斗执行
7. Party、AI、Encounter 组织玩法流程
8. Presentation、UI 订阅战斗事实并展示结果

这是主要依赖方向，不代表所有模块必须严格串成一条调用链

### 3.2 模块依赖约束表

跨模块依赖按下表逐项确定，同属 `Combat/` 的模块也遵循此约束。例如，HitDetection 通过 Weapons 的公开接口读取轨迹采样点，Skills 通过 Actions 的公开接口提交动作请求。各模块的内部实现仅供本模块使用

| 模块 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| Stats | Contracts | Damage、UI、Animation |
| Resources | Contracts、Stats 上限读取接口 | UI、AI |
| CharacterBuild | Stats | Damage、Presentation |
| Effects | Stats、Timing、必要的 Damage 契约 | UI、Animation |
| Status | Resources、Effects、Contracts | UI |
| Damage | Stats、Resources、Status、Contracts | Animation、UI |
| Animation | Contracts、Timing | Damage、Enemy AI |
| CharacterMotion | Animation 的运动数据接口 | Damage、UI |
| MotionWarping | Animation、CharacterMotion | UI、Damage |
| Actions | Animation、Motion、Timing、Contracts | UI |
| Weapons | Actors 的挂点接口 | Damage |
| HitDetection | Weapons、Actors、Actions | UI |
| Combos | Actions、Input、Contracts | Animation 内部实现 |
| Skills | Actions、Stats、Resources、Effects | UI |
| Party | Actors、Resources、Actions | Animation 内部实现 |
| AI | Actors、Party、Actions、目标接口 | Damage 内部公式 |
| Encounter | Actors、Party、AI | Stats 内部实现 |
| Presentation | 事实事件、Pooling、Timing | 业务结算 |
| UI | 只读数据和事实事件 | 直接修改战斗数据 |

### 3.3 关键依赖规则

**Damage 不依赖具体角色类**

Damage 接收攻击者快照、目标防御数据和 DamageContext，通过稳定契约完成计算

**Actions 不依赖动画内部实现**

Actions 通过动画驱动接口请求播放动作，Animation 实现具体 PlayableGraph 操作

**Stats 不依赖战斗表现**

属性变化可发布事件，但 Stats 不知道 UI、特效或音效如何展示

**Presentation 不决定战斗结果**

表现系统只能响应已经发生的事实，不能反向决定伤害是否成功

## 五、模块通信与运行时数据流

### 5.1 普通攻击数据流

```text
Input
  │
  ▼
ComboSystem
  │ 选择当前连招节点
  ▼
ActionSystem
  │ 验证并提交攻击动作
  ▼
Animation ───────── MotionWarping
  │ Playable 播放       │ 攻击轨迹修正
  └──────────┬──────────┘
             ▼
      Weapon + HitDetection
             │ 采样武器轨迹
             ▼
        DamageSystem
             │ 快照、计算、结算
             ▼
       Resources / Status
             │ HP、护盾、失衡、附着
             ▼
       Combat Fact Events
             │
             ▼
       Presentation + UI
```

攻击动作不直接扣除敌人 HP。命中检测生成 HitContext，DamageSystem 计算并应用伤害

### 5.2 通信方式

| 通信方式 | 用途 | 示例 |
| --- | --- | --- |
| 直接接口调用 | 必须立即获得执行结果 | 消耗 SP、提交动作 |
| 事实事件 | 广播已经发生的事实 | DamageApplied、ActorDied |

不要用异步事件完成必须原子提交的资源扣除。资源提交必须同步返回成功或失败

### 5.3 建议的模块公开能力

| 模块 | 能力方向 |
| --- | --- |
| Stats | GetValue、AddModifier、RemoveSource、Snapshot |
| Resources | Consume、Restore、ApplyDamage、SetMaximum |
| Effects | ApplyEffect、RemoveEffect |
| Status | ApplyStatus、ConsumeStatus、GetStatus |
| Damage | Calculate、Apply、GetBreakdown |
| Animation | Play、CrossFade、Stop |
| CharacterMotion | SubmitMotion、Move、Rotate |
| MotionWarping | BeginWarp、UpdateWarp、EndWarp |
| Actions | Request、Commit、Cancel |
| Weapons | Attach、Detach、GetTracePoints |
| HitDetection | BeginWindow、EndWindow、QueryHits |
| Combos | Advance、Reset、Evaluate |
| Skills | RequestSkill、CommitSkill |
| Party | SwitchMember、GetActiveMember |

以上是能力定义，不是要求现在立即创建这些方法。每个模块的具体 API 在对应模块设计阶段确定

## 九、跨模块技术规范

### 9.1 ActorRuntime 的组成

逻辑上一个 ActorRuntime 可以组合：

- CharacterBuild
- StatSet
- ResourceContainer
- EffectController
- StatusController
- ActionController
- Animation Driver
- CharacterMotor
- WeaponAttachment
- Targeting

以上是逻辑组成，不代表每项都必须成为 MonoBehaviour

优先使用普通 C# 类管理纯逻辑。只有需要 Unity 生命周期、Transform、Animator、Physics 或场景对象的部分才使用 MonoBehaviour

### 9.2 时间系统

必须区分：

| 时间类型 | 用途 |
| --- | --- |
| Real Time | UI、外部表现和真实时间 |
| Battle Time | 战斗逻辑、持续效果 |
| Action Time | 当前角色动作推进 |
| Presentation Time | 特效、音效等表现 |

PlayableGraph 必须有明确的求值模式

Hit Stop 不得通过随意修改全局 `Time.timeScale` 来实现局部角色顿帧

首版先验证角色级别局部顿帧与动作时间同步

### 9.3 运动控制权

强制遵循：

```text
Animation
    │
    ▼
Root Motion Delta
    │
    ▼
MotionWarping
    │
    ▼
CharacterMotor
    │
    ▼
CharacterController
    │
    ▼
ActorRoot
```

只有 CharacterMotor 最终应用 ActorRoot 位移

MotionWarping 只提供修正量，Animation 只提供动画和根运动数据

### 9.4 数据所有权

| 数据 | 唯一所有者 |
| --- | --- |
| 最终属性 | Stats |
| 角色成长来源 | CharacterBuild |
| 当前 HP | Resources |
| Buff 实例 | Effects |
| 元素附着与失衡状态 | Status |
| 单次伤害计算 | Damage |
| 当前动作 | Actions |
| 动画图 | Animation |
| 角色最终位置 | CharacterMotion |
| 当前队伍 | Party |
| 战斗波次 | Encounter |
| 临时特效对象 | Pooling |

不允许多个模块同时拥有同一份可变数据

## 十四、Codex 项目开发总规则

以下规则适用于之后所有模块任务

1. 当前项目处于重新设计和实现阶段。此前战斗系统代码实现已回撤，不得假设历史类、接口或目录仍然存在
2. 现有 Unity 工程、两个角色、武器、动画、美术资源和场景优先保留与复用
3. 一次只设计或实现用户明确指定的一个模块
4. 每个模块先审查、再设计、再评审、再实现、再测试、再验收
5. 未经批准不得实现其他模块
6. 未经批准不得修改已验收模块
7. 未经批准不得大规模重构目录
8. 不创建没有实际用途的空类、空目录或占位实现
9. 所有静态配置与运行时数据分离
10. Playables 是战斗动画播放核心
11. Motion Warping 是攻击运动系统
12. 角色位移必须经过统一 CharacterMotor
13. Effect、Audio 等临时对象必须使用对象池
14. Stats、CharacterBuild、Resources、Effects、Status、Damage 必须保持独立职责
15. 不得声称未执行的编译、测试或运行验证已经通过
16. 每次模块任务完成后停止，等待用户验收和下一条指令

```text
        ▼

        ▼

        │
        ▼
Codex implements only approved module
        │
        ▼
Codex runs tests and Unity verification
        │
        ▼
Codex submits acceptance report
        │
        ▼
User accepts and creates Git checkpoint
        │
        ▼
Next module
```

- [ ] 依赖关系已确认

**V2.0 的完成不代表战斗系统已经实现，而是意味着后续每一个模块都有明确的设计依据和实施边界**
