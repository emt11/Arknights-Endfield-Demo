# Unity 战斗系统 Architecture V2.0

**Combat System Architecture · Technical Design Baseline · V2.0**

- 项目：基于现有 Unity 工程的《明日方舟：终末地》风格战斗 DEMO
- 文档类型：总体架构规范（Architecture Specification）
- 用途：指导 Unity 客户端求职 Demo 的模块分工、技术评审和逐模块交付
- 当前阶段：重新设计与实现；此前战斗系统代码实现已回撤
- 本文范围：总体模块地图、职责边界、依赖关系、目录结构、实施顺序、验收规范
- 本文不包含：业务代码实现、场景修改、Prefab 修改、资源迁移

## 0. 项目基线与设计约束

### 0.1 项目现状

- 两个已有角色：大剑角色、双手剑角色

- 现有武器资源
- 现有环境与 CombatDemo 场景
- 现有输入配置，以及可复用的相机和 UI 资源

### 0.2 核心技术约束

| 领域 | 架构要求 |
| --- | --- |
| 战斗动画 | 使用 Unity Playables API 驱动 |
| 基础移动动画 | 可以使用 Animator Controller / AnimatorControllerPlayable |
| 攻击动画 | 使用 AnimationClipPlayable |
| 动画混合 | 使用 AnimationMixerPlayable、AnimationLayerMixerPlayable 等适合的 Playable |
| Root Motion | 统一提取、修正和消费 |
| Motion Warping | 自定义运动扭曲系统 |
| 角色移动 | 统一通过 CharacterMotor 应用最终位移 |
| 命中检测 | 武器轨迹连续扫掠 + Physics Query |
| 对象池 | Effect、Audio、Projectile、临时 UI 等复用对象统一池化 |
| 属性 | 独立 StatSystem |
| 角色成长 | 独立 CharacterBuild |
| 伤害 | 独立 DamageSystem |
| 配置 | 静态配置优先使用 ScriptableObject |
| 测试 | 使用 Unity Test Framework，按模块验收 |

### 0.3 全局架构原则

- 横向按领域划分模块，通过公开接口协作，每份可变数据有唯一所有者
- 静态配置和每个角色的运行时状态分开。模块内部按当前玩法选择数据结构和算法
- 对 Playables、Root Motion、武器扫掠等影响玩家体验的技术，明确执行时机和验证场景
- 模块任务按第七章实施，验收与接口变更按第八章记录

## 一、总体架构与领域分层

整个战斗系统划分为六个领域层。它们是逻辑职责分组，不是强制的程序集分组

### 1.1 Gameplay Orchestration：游戏流程层

包含：

- CombatSession
- Actors
- Party
- Input
- AI
- Encounter

负责战斗会话、角色组织、玩家输入、队伍管理、AI 决策和战斗流程

### 1.2 Character Foundation：角色基础层

包含：

- CharacterBuild
- Stats
- Resources
- Effects
- Status

负责角色构建、属性、动态资源、持续效果和战斗状态

### 1.3 Combat Execution：战斗执行层

战斗执行代码统一归入 `Assets/Scripts/Runtime/Combat/`，六个子模块各自维护公开接口和命名空间

| 子模块 | 核心职责 | 命名空间 |
| --- | --- | --- |
| Actions | 处理动作请求、执行、取消与时间轴窗口 | `Endfield.Combat.Actions` |
| Weapons | 管理武器定义、实例、骨骼挂载和轨迹采样点 | `Endfield.Combat.Weapons` |
| HitDetection | 在命中窗口内执行扫掠查询、筛选目标并生成命中上下文 | `Endfield.Combat.HitDetection` |
| Damage | 根据本次攻击保存的属性值计算伤害，通过资源接口应用结果并发布结算事件 | `Endfield.Combat.Damage` |
| Combos | 管理普攻连招树、输入缓存、分支和连招游标 | `Endfield.Combat.Combos` |
| Skills | 管理战技与终结技的请求、消耗和冷却，通过 Actions 提交动作 | `Endfield.Combat.Skills` |

### 1.4 Animation & Motion：动画与运动层

包含：

- Animation
- CharacterMotion
- MotionWarping

负责 PlayableGraph、动画混合、角色移动、Root Motion 和 Motion Warping

### 1.5 Infrastructure：基础设施层

包含：

- CombatContracts
- Timing
- Pooling
- Diagnostics

负责跨模块数据契约、时间管理、对象池和调试诊断

### 1.6 Presentation：表现层

包含：

- Presentation
- UI

负责特效、音效、镜头反馈、伤害数字、战斗 HUD 和状态显示

## 二、完整模块地图与职责边界

### 2.1 Gameplay Orchestration

#### 01. CombatSession

**职责**

- 创建和销毁一次战斗会话
- 管理战斗生命周期
- 组织模块初始化和清理
- 绑定现有场景中的战斗引用
- 管理战斗重试和重置

**不负责**

- 逐帧执行攻击逻辑
- 伤害公式
- 敌人 AI 决策

#### 02. Actors

**职责**

- 定义战斗单位身份
- 管理阵营和阵营关系
- 组合角色运行时模块
- 提供统一 Combatant 能力
- 管理单位存活状态和生命周期

**不负责**

- 装备成长计算
- 伤害公式
- 动画图内部播放逻辑

#### 03. Party

**职责**

- 管理队伍成员和槽位
- 管理当前操控角色
- 角色切换
- 队伍共享资源
- 队友与队伍协同规则

首版只要求两个有效角色，数据结构支持四个槽位。四槽位架构不等于首版必须制作四个完整角色

#### 04. Input

**职责**

- 接收 Unity Input System 输入
- 生成输入命令
- 管理输入缓存
- 处理输入优先级和过期

**不负责**

- 直接播放动画
- 直接扣除敌人生命值
- 绕过 ActionSystem 执行动作

#### 05. AI

**职责**

- 敌人决策
- 队友辅助决策
- 目标选择
- 攻击策略
- 移动与战斗站位决策

玩家输入和 AI 决策最终通过统一的动作请求接口执行。首版优先使用有限状态机与简单选择器，不预先开发通用行为树编辑器

#### 06. Encounter

**职责**

- 敌人生成
- 波次管理
- Boss 阶段
- 战斗胜负条件
- 战斗流程编排

**不负责**

- 敌人每一帧的攻击行为
- 伤害计算
- 角色动画播放

### 2.2 Character Foundation

#### 07. CharacterBuild

**职责**

- 角色基础属性来源
- 等级成长
- 主属性、副属性
- 武器属性聚合
- 装备和天赋属性聚合
- 生成角色初始 StatSet

**不负责**

- 属性修改器底层计算
- 伤害公式
- Buff 生命周期

#### 08. Stats

每名角色持有独立的属性面板。Stats 根据角色初值、主副属性和有效修正计算最终值，按来源更新或撤销词条。一次写入完成后，调用方读到同一轮计算的面板，重复读取直接使用缓存。最终值发生变化时，Stats 通知订阅者

- **首批面板**覆盖四维、基础攻防与生命、武器和固定攻击、攻击加成、ATK、DEF、MaxHP 与暴击率。抗性、治疗加成和特殊属性随消费它们的玩法接入
- **边界**由 Stats 持有最终属性和 MaxHP，Resources 持有 CurrentHP，Status 持有脆弱等状态层数。Damage 通过只读接口取得结算输入
- **数值依据**沿用《设计属性系统.txt》中的主副属性与来源修正思路。公式、系数及可复算样例按 Demo 约定记录在 [M1.1 StatSystem 详细技术设计](./M1.1%20StatSystem%20详细技术设计.md)

#### 09. Resources

**职责**

- HP 当前值
- SP
- 终结技能量
- 护盾
- 失衡槽等动态资源

边界规则：

- MaxHP 属于 Stats
- CurrentHP 属于 Resources
- MaxSP 属于 Stats 或相应上限配置
- CurrentSP 属于 Resources
- 护盾实例由 Resources 管理
- 失衡状态转换由 Status 管理，失衡数值槽可由 Resources 或 Status 内部专用数据管理，但必须确定唯一所有者

#### 10. Effects

**职责**

- Buff、Debuff 生命周期
- 持续时间
- 周期性效果
- 叠加策略
- 来源追踪
- 按效果实例向 Stats 提交或撤销整组属性修正
- 添加和移除 DamageModifier

**不负责**

- 元素附着规则
- 伤害命中判定
- 直接控制动画

#### 11. Status

**职责**

- 元素附着
- 脆弱
- 控制状态
- 失衡状态转换
- 元素反应
- 状态层数和消费规则

Status 持有附着、脆弱、失衡等状态及层数，对外提供施加、查询和消费入口。持续效果实例及其计时归 Effects

### 2.3 Combat Execution

#### 12. Actions

**职责**

- 动作请求和提交
- ActionInstance 生命周期
- 动作取消
- 动作优先级
- 动作时间轴
- 动作窗口管理

ActionSystem 是动作执行协调者，不是动画播放器

#### 13. Weapons

**职责**

- 武器定义
- 武器 Prefab 实例
- 武器骨骼挂载
- 武器局部偏移
- 武器轨迹采样点

**不负责**

- 攻击伤害结算
- 目标 HP 修改

#### 14. HitDetection

**职责**

- Blade Sweep
- SphereCast / CapsuleCast
- 范围命中查询
- Hit Window 管理
- 命中目标筛选
- AttackID / HitWindowID 去重
- HitContext 生成

**不负责**

- 最终伤害公式
- Buff 生命周期
- UI 反馈

#### 15. Damage

**职责**

- 在动作约定的时点保存本次攻击需要的属性值
- DamageContext
- DamageModifier
- 暴击计算
- 防御和抗性
- 伤害乘区
- DamageBreakdown
- DamageResult
- 伤害应用和结算事件

DamageSystem 不负责判断攻击是否命中，也不直接修改角色基础属性

#### 16. Combos

**职责**

- 普攻连招树
- 连招输入窗口
- 连招输入缓存
- 分支条件
- 连招循环
- 连招游标管理

普攻连招和队伍连携是不同机制。队伍连携归 Party 或 Party 内的 TeamCombo 子模块

#### 17. Skills

**职责**

- 战技请求
- 终结技请求
- 技能冷却
- 技能资源消耗
- 目标要求
- 技能动作配置
- 技能效果触发

技能通过 Actions 执行动作，不直接实现另一套动画播放系统

### 2.4 Animation & Motion

#### 18. Animation

**职责**

- PlayableGraph 生命周期
- AnimatorControllerPlayable 基础动画输入
- AnimationClipPlayable 战斗动画
- AnimationMixerPlayable 动作混合
- AnimationLayerMixerPlayable 动画层
- 动画速度与时间控制
- 动画混合与退出

**不负责**

- 角色最终位移
- 攻击命中
- 伤害结算

#### 19. CharacterMotion

**职责**

- CharacterMotor
- 地面检测
- 重力
- 移动和转向
- Root Motion 消费
- 外部冲量
- 碰撞约束
- 最终 Transform 运动应用

所有角色位移必须通过 CharacterMotor

#### 20. MotionWarping

**职责**

- Root Motion 轨迹采样数据
- MotionProfile
- Warp Target
- Warp Window
- 位移补偿
- 旋转修正
- 碰撞反馈
- 目标丢失处理

MotionWarping 提供受约束的运动修正，不直接修改 Transform.position

### 2.5 Infrastructure

#### CombatContracts

只放跨模块共享的稳定数据契约、标识、接口和上下文。不得成为无边界的 Common 或 Utils 收纳目录

#### Timing

负责战斗时间、动作时间、暂停、慢速和局部 Hit Stop 的时间规则。PlayableGraph 的更新模式必须在技术验证阶段确定

#### Pooling

负责对象租用、归还、重置、预热、容量管理和会话清理。Effect、Audio、Projectile、临时 UI 等按生命周期纳入对象池

#### Diagnostics

负责战斗事件追踪、属性调试、动作调试、运动轨迹诊断和必要的性能诊断

### 2.6 Presentation

#### Presentation

负责特效、音效、镜头震动、Hit Flash、Hit Stop 表现请求、伤害数字等视觉与听觉反馈。临时对象通过 Pooling 获取和归还

#### UI

负责 HUD、角色面板、技能状态、敌人血条、状态图标和调试展示。UI 只读取数据和订阅事件，不拥有战斗业务数据

## 三、模块依赖关系

### 3.1 总体依赖原则

建议采用以下依赖层次：

1. Foundation / Contracts 提供稳定基础类型
2. Stats、Resources 提供独立数据能力
3. CharacterBuild、Effects、Status 通过公开接口使用基础数据能力
4. Actors 组合角色运行时模块
5. Animation、CharacterMotion、MotionWarping 提供动画与运动能力
6. Actions、Weapons、HitDetection、Damage、Combos、Skills 组织战斗执行
7. Party、AI、Encounter 组织玩法流程
8. Presentation、UI 订阅战斗事实并展示结果

这是主要依赖方向，不代表所有模块必须严格串成一条调用链

### 3.2 模块依赖约束表

跨模块依赖按下表逐项确定，同属 `Combat/` 的模块也遵循此约束。例如，HitDetection 通过 Weapons 的公开接口读取轨迹采样点，Skills 通过 Actions 的公开接口提交动作请求。各模块的内部实现仅供本模块使用

| 模块 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| Stats | Contracts | Damage、UI、Animation |
| Resources | Contracts、Stats 上限读取接口 | UI、AI |
| CharacterBuild | Stats | Damage、Presentation |
| Effects | Stats、Timing、必要的 Damage 契约 | UI、Animation |
| Status | Resources、Effects、Contracts | UI |
| Damage | Stats、Resources、Status、Contracts | Animation、UI |
| Animation | Contracts、Timing | Damage、Enemy AI |
| CharacterMotion | Animation 的运动数据接口 | Damage、UI |
| MotionWarping | Animation、CharacterMotion | UI、Damage |
| Actions | Animation、Motion、Timing、Contracts | UI |
| Weapons | Actors 的挂点接口 | Damage |
| HitDetection | Weapons、Actors、Actions | UI |
| Combos | Actions、Input、Contracts | Animation 内部实现 |
| Skills | Actions、Stats、Resources、Effects | UI |
| Party | Actors、Resources、Actions | Animation 内部实现 |
| AI | Actors、Party、Actions、目标接口 | Damage 内部公式 |
| Encounter | Actors、Party、AI | Stats 内部实现 |
| Presentation | 事实事件、Pooling、Timing | 业务结算 |
| UI | 只读数据和事实事件 | 直接修改战斗数据 |

### 3.3 关键依赖规则

**Damage 不依赖具体角色类**

需要锁定攻击属性时，Damage 在动作约定的时点通过 Stats 只读接口复制所需数值，之后结合目标防御数据和 DamageContext 结算。单次攻击使用的副本由 Damage 持有

**Actions 不依赖动画内部实现**

Actions 通过动画驱动接口请求播放动作，Animation 实现具体 PlayableGraph 操作

**Stats 不依赖战斗表现**

属性变化可发布事件，但 Stats 不知道 UI、特效或音效如何展示

**Presentation 不决定战斗结果**

表现系统只能响应已经发生的事实，不能反向决定伤害是否成功

### 4.1 目录组织规则

`Runtime/Combat/` 只收纳第 1.3 节的六个执行模块。`Animation`、`CharacterMotion`、`MotionWarping`、`Stats`、`Resources`、`Effects` 等系统各自在 `Runtime/` 下维护，向战斗模块提供公开能力

| 内容 | 存放位置 |
| --- | --- |
| C# Runtime 代码 | Scripts/Runtime 对应模块 |
| ScriptableObject 类型 | Scripts/Runtime 对应模块 |
| ScriptableObject 实例 | ScriptObjects |
| Prefab 实例 | Prefabs |
| Unity Editor 工具 | Scripts/Editor |
| 自动化测试 | Scripts/Test 下的对应模块 |
| 原有模型、贴图、动画 | 保留原 Art 资源位置 |
| 原有场景 | 保留原路径、名称和 GUID |

### 4.2 Assembly Definition 策略

第一阶段不强制每个目录建立 asmdef

各战斗子模块使用第 1.3 节列出的独立命名空间，分别测试和验收。需要拆分程序集时，按实际接口依赖划分 asmdef

可以考虑的程序集边界：

- Foundation / Contracts
- Character Data
- Combat Runtime
- Animation Runtime
- Gameplay
- Presentation
- Editor
- Tests

不允许为了目录数量而创建大量程序集

## 五、模块通信与运行时数据流

### 5.1 普通攻击数据流

```text
Input
  │
  ▼
ComboSystem
  │ 选择当前连招节点
  ▼
ActionSystem
  │ 验证并提交攻击动作
  ▼
Animation ───────── MotionWarping
  │ Playable 播放       │ 攻击轨迹修正
  └──────────┬──────────┘
             ▼
      Weapon + HitDetection
             │ 采样武器轨迹
             ▼
        DamageSystem
             │ 读取本次攻击所需数值、计算并结算
             ▼
       Resources / Status
             │ HP、护盾、失衡、附着
             ▼
       Combat Fact Events
             │
             ▼
       Presentation + UI
```

攻击动作不直接扣除敌人 HP。命中检测生成 HitContext，DamageSystem 计算并应用伤害

### 5.2 通信方式

| 通信方式 | 用途 | 示例 |
| --- | --- | --- |
| 直接接口调用 | 必须立即获得执行结果 | 消耗 SP、提交动作 |
| 事实事件 | 广播已经发生的事实 | DamageApplied、ActorDied |

不要用异步事件完成必须原子提交的资源扣除。资源提交必须同步返回成功或失败

### 5.3 建议的模块公开能力

| 模块 | 能力方向 |
| --- | --- |
| Stats | 读取最终值、写入基础值、按来源替换或移除词条、订阅面板变化 |
| Resources | Consume、Restore、ApplyDamage、SetMaximum |
| Effects | ApplyEffect、RemoveEffect |
| Status | ApplyStatus、ConsumeStatus、GetStatus |
| Damage | Calculate、Apply、GetBreakdown |
| Animation | Play、CrossFade、Stop |
| CharacterMotion | SubmitMotion、Move、Rotate |
| MotionWarping | BeginWarp、UpdateWarp、EndWarp |
| Actions | Request、Commit、Cancel |
| Weapons | Attach、Detach、GetTracePoints |
| HitDetection | BeginWindow、EndWindow、QueryHits |
| Combos | Advance、Reset、Evaluate |
| Skills | RequestSkill、CommitSkill |
| Party | SwitchMember、GetActiveMember |

以上是能力定义，不是要求现在立即创建这些方法。每个模块的具体 API 在对应模块设计阶段确定

## 七、模块独立实施规范

| 阶段 | 交付与评审 |
| --- | --- |
| 工程审查 | 核对当前模块的资源、依赖、调用方和已知风险 |
| 详细设计 | 每个模块保留一份详设，说明数据归属、公开接口、运行流程和可验证的结果。Stats 写清数值算例，Motion Warping 则需写清采样、目标变化和碰撞约束 |

## 八、统一验收状态与冻结规则

### 8.1 状态定义

| 状态 | 含义 |
| --- | --- |
| Not Started | 尚未开始 |
| In Progress | 正在实现 |
| Verified | 测试与验收通过 |
| Blocked | 存在未解决问题 |

不使用含糊的 Done 表示代码写完但没有验证

### 8.2 模块验收标准

| 检查 | 验收依据 |
| --- | --- |
| 边界 | 调用方仅依赖公开接口，数据所有者明确，依赖无环 |
| 行为 | 用 EditMode 验证可复算的逻辑和关键失败路径。涉及动画、物理、切换和销毁的行为用相应的 Play Mode 场景验证 |
| 构建与记录 | 记录 Unity 编译结果和本次实际执行的用例。涉及平台行为时补充 Player 验证，单独列出尚待验证的范围 |

### 8.3 冻结规则

模块进入 Verified 后：

- 其他模块只能通过公开接口使用
- 不允许直接修改内部实现
- 接口变更必须提出变更申请
- 说明受影响模块
- 更新相关测试
- 重新验收受影响模块

Git 检查点可使用稳定提交或 Tag

## 九、跨模块技术规范

### 9.1 ActorRuntime 的组成

逻辑上一个 ActorRuntime 可以组合：

- CharacterBuild
- StatSet
- ResourceContainer
- EffectController
- StatusController
- ActionController
- Animation Driver
- CharacterMotor
- WeaponAttachment
- Targeting

以上是逻辑组成，不代表每项都必须成为 MonoBehaviour

优先使用普通 C# 类管理纯逻辑。只有需要 Unity 生命周期、Transform、Animator、Physics 或场景对象的部分才使用 MonoBehaviour

### 9.2 时间系统

必须区分：

| 时间类型 | 用途 |
| --- | --- |
| Real Time | UI、外部表现和真实时间 |
| Battle Time | 战斗逻辑、持续效果 |
| Action Time | 当前角色动作推进 |
| Presentation Time | 特效、音效等表现 |

PlayableGraph 必须有明确的求值模式

Hit Stop 不得通过随意修改全局 `Time.timeScale` 来实现局部角色顿帧

首版先验证角色级别局部顿帧与动作时间同步

### 9.3 运动控制权

强制遵循：

```text
Animation
    │
    ▼
Root Motion Delta
    │
    ▼
MotionWarping
    │
    ▼
CharacterMotor
    │
    ▼
CharacterController
    │
    ▼
ActorRoot
```

只有 CharacterMotor 最终应用 ActorRoot 位移

MotionWarping 只提供修正量，Animation 只提供动画和根运动数据

### 9.4 数据所有权

| 数据 | 唯一所有者 |
| --- | --- |
| 最终属性 | Stats |
| 角色成长来源 | CharacterBuild |
| 当前 HP | Resources |
| Buff 实例 | Effects |
| 元素附着与失衡状态 | Status |
| 单次伤害计算 | Damage |
| 当前动作 | Actions |
| 动画图 | Animation |
| 角色最终位置 | CharacterMotion |
| 当前队伍 | Party |
| 战斗波次 | Encounter |
| 临时特效对象 | Pooling |

不允许多个模块同时拥有同一份可变数据

## 十、风险管理与技术验证

### 10.1 高风险技术

| 技术 | 风险 | 验证要求 |
| --- | --- | --- |
| PlayableGraph | 动画求值与 Root Motion 同步 | 独立验证 |
| Humanoid Root Motion | 预采样与运行时轨迹差异 | Avatar 对照 |
| Motion Warping | 碰撞与目标位移冲突 | 移动目标测试 |
| FootPlanting | 脚部滑动和骨盆漂移 | 独立动画验证 |
| Weapon Trace | 高速攻击漏判 | 连续扫掠测试 |
| Local Hit Stop | 多角色时间不同步 | 多角色测试 |

### 10.2 中风险技术

- 增益到期后 ATK 未恢复，或误删同模板的另一个来源
- 属性变更后 HUD 或伤害结算读到过期值，或已锁定的攻击数值被后续 Buff 改写
- Buff 与 Status 生命周期
- Pool Generation
- Action 取消清理
- 角色切换与动画图生命周期

这些都应该具有自动化测试

### 10.3 工程风险

- ScriptableObject GUID 丢失
- Prefab 序列化引用断裂
- 多模块循环依赖
- 角色动画资源不完整
- 场景入口绑定错误
- Editor 代码进入 Player 构建

这些风险在 M0 检查并在后续持续验证

## 十四、Codex 项目开发总规则

每次任务限定在用户指定的模块和交付物内。复用现有角色、武器、动画和场景，保留资源路径与 GUID。涉及已验收模块或大规模目录变更时先提交影响范围，由用户确认
