# M2.3 Status 战斗状态详细技术设计 V1.1

**已实现 · Unity 定向验收通过**　Status 负责回答“目标有几层脆弱、附着哪种元素、是否被冻结或失衡”

目标身上的时长统一由 Effects 推进，失衡槽读数统一由 Resources 维护 · [M2 阶段总览](./M2%20Runtime%20Foundation%20开发设计.md)

## 1. 首版玩法与数据归属

以下为本版 Demo 使用的规则及验收参数，`StatusRuleProfile` 配置层数上限、每层增幅并引用各状态的计时模板

热、冰用于走通第一条附着与反应链，电和自然随相应招式扩展 · [已有元素设计](../M1/M1.1%20StatSystem%20详细技术设计.md#13-元素相关属性与启用条件)

| 状态 | 施加与消费 | 到期行为 |
| --- | --- | --- |
| 脆弱 `Vulnerable` | 每层使目标承受的物理伤害增加 10%，最多 3 层<br>同种叠层共用一个 5 秒计时，重复施加刷新时长，普通命中只读取层数，明确配置为消费的操作才扣层 | 时间到清空剩余层数，提前消费到 0 时移除对应计时 |
| 热 / 冰附着 `Heat / Cryo` | 每个目标一个附着槽，最多 2 层，持续 5 秒<br>同元素叠层并刷新，首次施加占用空槽<br>本版定义“已有热、受到冰附着”触发冻结并消耗全部热，本次冰不再入槽<br>其余异种组合用新附着替换旧附着 | 附着到期清空该槽<br>伤害类型与是否施加元素分别配置，一次术式伤害可以完全不施加附着 |
| 冻结 `Frozen` | 热与冰反应后进入 2 秒控制状态，再次触发刷新时长<br>后续 Actions 读取控制状态决定是否接受动作 | 只解除冻结，其他控制原因继续生效 |
| 失衡 `Staggered` | 通过 `AddStagger` 使积累首次达到正阈值时进入，持续 2 秒，期间槽保持满值 | 退出失衡时调用 `ResetStagger()` 清槽，之后可重新积累 · [Resources 的失衡规则](../M1/M1.2%20Resources%20详细技术设计.md#3-sp终结技能量与失衡) |

Status 保存每个状态的类型、层数和对应效果句柄

每种状态的持续秒数只填写在对应的纯计时 `EffectProfile` 中，Effects 用战斗秒数推进，Status 订阅结束通知并按句柄清除对应状态 · [Effects 计时入口](./M2.2%20Effects%20详细技术设计.md)

规则资产的 `int maxVulnerableStacks` 填 3，`double physicalBonusPerStack` 填 0.10，`int maxAttachmentStacks` 填 2。四个 `EffectProfile` 字段中，`vulnerableTimer` 和 `attachmentTimer` 引用 5 秒模板，`frozenTimer` 和 `staggeredTimer` 引用 2 秒模板。每个状态单独持有实例句柄，共用模板的冻结与失衡可以分别到期

控制器以 `Dictionary<StatusType, (int Stacks, EffectHandle Timer)> active` 持有当前状态，出生时为空。每条记录的 `int Stacks` 是已提交层数，冻结与失衡取 1，`EffectHandle Timer` 取自 Effects 的施加结果。Status 在施加、消费或计时结束时更新记录，Damage 读取物理承伤倍率，动作层读取控制状态

## 2. 接入组件与公开接口

`CharacterStatus` 挂在目标角色的逻辑根，Inspector 的 `StatusRuleProfile rules` 引用规则资产，`Awake` 按顺序 −30 执行，取得已初始化的 `CharacterResources.Container`、`CharacterEffects.Controller` 和自身只读面板，创建一个 `StatusController`

运行时目录为 `Assets/Scripts/Runtime/Status/`，命名空间为 `Endfield.Status`

| 公开入口 | 含义 |
| --- | --- |
| `GetStacks(type)`、`IsActive(type)`、`PhysicalDamageTakenMultiplier` | 空状态返回 0 层，物理承伤倍率为 `1 + 脆弱层数 × 每层增幅`<br>冻结和失衡分别可查询，两者同时存在时任一仍可限制动作 |
| `ApplyVulnerable(stacks)`、`ApplyAttachment(element, stacks)` | 对正的层数输入按规则叠层、封顶或触发反应，返回本次提交后的状态变化<br>反应由 Status 解释，Damage 通过独立的附着配置决定是否调用 |
| `TryConsume(type, count)` | 对可消费的脆弱或附着一次扣足正数量，层数不足返回 false，保持剩余层数与原到期时刻 |
| `ApplyStagger(amount)` | 通过目标容器提交非负积累量，以返回值决定是否进入失衡<br>无失衡阈值或本次未跨阈值时可从资源快照读取实际积累 |
| `Subscribe(listener) → IDisposable` | 一次状态操作发布一条变化，列出改变的类型及旧、新层数，一次反应中订阅者直接读到“热为空、冻结已生效”的最终状态 |

施加脆弱或附着返回 `IReadOnlyList<StatusChange>`，每项包含 `Type`、`PreviousStacks`、`CurrentStacks`。封顶后再次施加仍刷新时长，变化记录的旧、新层数相同。`ApplyStagger` 仅在本次跨过正阈值、进入失衡时返回 true。`TryConsume` 拒绝不可消费的控制状态，失败时保留原状态与计时

切换操控权保留状态，销毁角色时先释放结束订阅，再清理该控制器持有的计时句柄

## 3. 反应与失衡的提交顺序

**热遇冰**　先按攻击到达前的附着确定反应，创建或刷新冻结计时并记录冻结，再解绑热与旧句柄并移除旧计时，最后发布包含热和冻结的同一批变化。只有最终状态对 Status 监听器可见

移除旧计时前解除旧句柄与槽位的关联，旧句柄的结束回调只处理仍与其匹配的状态

失效的旧计时不能清除刚写入的新状态

**失衡进入**　目标为 80/100 时，`resources.AddStagger(35)` 返回 true，资源快照为 100/100

资源调用返回后 Status 登记失衡和计时并发布进入通知，满槽再加不会刷新时长

初始化时先核对规则资产和纯计时模板，保证满槽转换有可用的计时配置 · [角色资源实现](../../Assets/Scripts/Runtime/Resources/Character/CharacterResourceContainer.cs)

**失衡退出**　计时到期时移除失衡标记并调用 `ResetStagger()`，再发布退出通知

此时状态监听器读到失衡已解除、槽值为 0，若还有冻结，则冻结仍可查询

## 4. 阶段验收

测试放在 `Assets/Scripts/Test/Editor/Status/`，在 EditMode 选择 `Endfield.Status.Tests`，使用真实资源容器与 Effects 控制器直接推进秒数

| 用例 | 操作与预期 |
| --- | --- |
| 脆弱封顶、消费和刷新 | 先加 2 层，两秒后再加 2 层，读到 3 层、物理承伤倍率 1.30<br>消费 4 层失败，消费 2 层后余 1 层、倍率 1.10，从第二次施加算满 5 秒后清空 |
| 附着、反应与过期回调 | 先施加热 2 层，4 秒后施加冰 1 层，热和冰均为 0，冻结生效<br>再过 1 秒，原热截止时刻不会解除冻结，再过 1 秒冻结结束<br>单独施加冰只得到冰附着 |
| 失衡只触发一次 | 对阈值 100 的目标先加 80，再加 35、10<br>只收到一次进入通知，暂停传 0 后仍为 100/100，推进 2 秒退出，槽为 0，再加 100 可再次进入<br>阈值为 0 的目标始终为 0 且没有状态通知 |

### 实际验收记录

Unity 6000.3.28f1 中，3 项 `StatusControllerTests` 全部通过。验证了脆弱刷新后的到期时刻、一次反应的完整变化通知、冰遇热时的替换，以及失衡到期清槽后仍保留冻结。阈值为 0 的目标未产生失衡通知。场景用例进一步验证 `Characters/PlayerRoot` 的冻结受战斗暂停和半速控制
